1. Hardware is a concurrent state machine, not a slow program

Register-transfer level, or RTL, describes how stored values move through combinational logic between clock events. A software function usually gives you a convenient sequential narrative: execute statement one, then statement two. Hardware descriptions instead elaborate into multiple structures that exist together. Two adders do not take turns merely because their descriptions appear on adjacent lines. They can evaluate concurrently, subject to propagation delays and physical implementation. Thinking in terms of state and next-state functions is more useful than imagining a processor interpreting every RTL line.

Combinational logic has outputs determined by current inputs, without intentional remembered state. An AND gate, multiplexer, and integer addition network are examples. Sequential logic remembers values, commonly in flip-flops updated on a clock edge. A register does not continuously follow its input: it samples according to its clocking rules. A clock is a timing reference, not a magical guarantee that every signal is valid. Physical setup and hold requirements, clock skew, and metastability all matter. Our early examples abstract these effects so we can reason about functional behavior first.

Consider two registers whose next values are a_next = b and b_next = a. At a rising edge they exchange their old values. They do not both become old b, as a careless sequential Python translation might suggest. Nonblocking assignments in clocked SystemVerilog are designed to express this old-state/next-state distinction. Conversely, a combinational process must assign outputs on every path when it is intended to describe purely combinational logic; otherwise unintended retained values can imply latches. Tool warnings are evidence to investigate, not decorations to suppress until a build turns green.

A chip lifecycle begins with requirements and architecture, then moves through microarchitecture, RTL implementation, verification, synthesis, physical implementation, timing and physical checks, manufacturing preparation, fabrication, packaging, and post-silicon bring-up. These activities overlap and feed back into one another. Verification is not one final test stage after RTL is “done.” An architectural decision can make a later property difficult to observe or prove. A reset policy established early may determine whether firmware can recover from an error without a power cycle.

A system-on-chip, or SoC, integrates processors, memories, accelerators, interconnects, peripherals, and control logic. A block is a smaller unit such as a FIFO, arbiter, or DMA engine. Correct blocks can compose into a broken SoC if their assumptions disagree: one block expects reset to flush outstanding requests while another expects all requests to complete. Integration verification therefore checks contracts between components, not merely the sum of block test results. This is familiar to distributed-systems engineers, except hardware contracts also contain cycle-level timing and finite-width arithmetic.

Worked decision. A team asks whether a 32-bit counter “overflows safely.” First specify unsigned versus signed interpretation, whether arithmetic wraps or saturates, and what software sees at the boundary. Then test the transition from the largest representable value. Python's arbitrary-precision integer is not a correct oracle unless you explicitly mask or range-check it. A beautifully written test can certify the wrong arithmetic if it models a different machine.

Review. Explain why a queue with correct contents can still be wrong if it raises ready one cycle late. The missing idea is that the contract includes timing and throughput, not only eventual values. Technical starting point: Verilator overview, which describes translating HDL into executable C++ or SystemC models rather than treating HDL as ordinary software.

2. What each verification platform can and cannot establish

Pre-silicon verification studies models before manufactured silicon exists. Post-silicon validation studies real devices after fabrication. Neither replaces the other. Simulation executes a model under chosen inputs and observes behavior. It is excellent for detailed debug and checking explicit traces, but the number of possible histories grows rapidly. Passing a million seeds does not mean all histories were explored, especially when constraints keep selecting nearly identical scenarios. A seed is a reproducibility aid, not a unit of proof.

RTL simulation commonly models discrete events and logical values. Gate-level simulation uses a lower-level netlist and can include timing annotations when configured, but it is typically more expensive and still depends on the model and setup. An untimed software reference model may specify functional outputs without describing every implementation cycle. That abstraction is valuable: a reference model copied line-for-line from RTL can reproduce the same mistake. The price of abstraction is an explicit adapter explaining when outputs are compared and which internal scheduling choices are intentionally ignored.

Hardware emulation maps a design into specialized hardware to execute long workloads faster than many software simulations. FPGA prototyping maps a design into programmable devices, often useful for firmware or system development. These approaches have different compilation costs, visibility limits, interface adaptations, and resource constraints. A bug that is easy to inspect in a short block simulation may be hard to localize after a long emulation run. An FPGA clocking or memory substitution may also differ from the intended ASIC implementation. Record these differences rather than describing a prototype as identical silicon.

Formal verification asks mathematical questions about a model. Bounded model checking can find a counterexample within a specified depth; absence of a counterexample to that depth is not automatically an unbounded proof. Induction and other engines can establish broader results under their assumptions. A proven property that never mentions data ordering cannot establish FIFO ordering. A proof with impossible environmental assumptions may be vacuous: it succeeds because no meaningful behavior is allowed. The SymbiYosys FIFO tutorial illustrates properties, bounded checks, covers, and counterexample traces.

Static techniques inspect structure or constraints without running ordinary input sequences. Lint catches many suspicious coding patterns. Clock-domain crossing analysis, reset-domain crossing analysis, static timing analysis, and equivalence checking answer different questions. A two-flop synchronizer may address a single-bit crossing but cannot by itself guarantee coherent transfer of a multi-bit counter. Timing closure does not prove a protocol is correct. Logical equivalence between two versions can preserve a pre-existing functional bug. Read every report as a scoped statement with explicit assumptions.

Post-silicon work adds real electrical behavior, process variation, temperature, power delivery, manufacturing defects, and actual system interactions. Observability is scarce compared with simulation; trace buffers, performance counters, scan-related facilities, and firmware instrumentation become important. You cannot assume every internal signal is freely inspectable. Nor does a clean device run prove that all corner conditions are safe. A model limitation discovered in silicon should feed back into future pre-silicon plans, not remain an isolated lab anecdote.

Worked decision. A rare ordering failure appears after hours of software boot. Use emulation or prototyping to reach the workload, capture a compact transaction trace, and reduce it into a focused simulation when possible. Use formal properties on the suspected queue or arbiter for generality. Do not demand that one platform be best at workload length, internal visibility, physical realism, and exhaustive state exploration simultaneously. Review: name the strongest claim a 50-cycle bounded check supports, and explicitly state what it does not establish.

3. The evidence pipeline: specification to signoff

A specification is a collection of obligations, not merely a PDF. Extract each obligation into an identifiable requirement with legal inputs, expected behavior, timing, reset effects, and error handling. “Supports streaming” is too vague to test. “When valid and ready are high at a rising edge, exactly one word is accepted” is actionable. Ambiguities should become questions with owners and dates, not undocumented choices buried in a testbench. A requirement ID lets a reviewer trace a test failure back to the promise that made it a failure.

A test plan maps those requirements into methods. Some obligations need directed tests, others constrained-random scenarios, assertions, formal proofs, static checks, or integration workloads. The plan should explain the checker, not just the input generator. Generating unusual traffic is not useful if no observer can recognize incorrect behavior. Include negative scenarios where the environment violates assumptions if the product promises detection or recovery. Do not silently expand the DUT's responsibility to include every imaginable illegal input.

Stimulus is what the test environment drives. A monitor observes what actually occurred. These are different: asking a driver to transmit ten words does not prove the DUT accepted ten words. Backpressure may prevent acceptance. Monitors should use the protocol's transfer event, not the driver's intention. A scoreboard predicts and compares results. For our FIFO, it maintains an independent queue of accepted input words and compares each accepted output with the oldest expected word. Its state must reset according to the same documented interface contract.

Coverage measures which planned situations were observed. Functional coverage captures meaningful behaviors such as “pop and push at full occupancy.” Code coverage captures structural activity such as executed statements, branches, or toggles. Neither is an oracle of correctness. A test can hit every planned bin while its scoreboard is disabled. Conversely, a real bug can appear in a scenario the coverage plan forgot to represent. Coverage helps direct investigation; it does not replace assertions, scoreboards, review, or judgment about missing requirements.

Triage separates failures into actionable classes: RTL bug, testbench bug, reference-model bug, configuration error, infrastructure error, specification ambiguity, or expected negative-test result. Bucketing similar failures reduces repeated work, but a signature can merge distinct root causes. Keep representative artifacts and allow engineers to split buckets. A regression is a repeatable collection of builds and runs across configurations and seeds. It must distinguish test failures from missing results, killed jobs, expired licenses, disk exhaustion, and incompatible compiled artifacts.

Signoff is a risk decision backed by evidence. It includes reviewed requirement coverage, passing relevant regressions, understood exclusions, issue disposition, static and formal results, and known limitations. It should not be delegated to one percentage. Waiving an unreachable bin changes the interpretation of coverage; record the reason, reviewer, applicable configuration, and evidence. If the requirement changes, revisit the waiver. “It has always been waived” is not a technical argument.

Worked chain. Requirement F4 says stalled output remains stable. A directed test fills the FIFO, holds the consumer unready, and keeps presenting producer data. A passive monitor records output valid, output data, ready, and reset at every edge. An assertion checks stability across each stalled interval. A functional bin records a stall lasting at least three cycles. The regression preserves the seed, RTL revision, and failure window. The reviewer can now inspect a complete chain rather than trust the sentence “backpressure tested.” Review: identify which artifact would expose a driver that claims success without seeing a handshake.

4. A precise ready/valid FIFO contract

A FIFO is a first-in, first-out queue. Our teaching FIFO has depth four, one clock, eight-bit words, an active-high synchronous reset, and no empty bypass. It exposes in_valid, in_ready, in_data, out_valid, out_ready, and out_data. All transfers are determined from values immediately before a rising edge. State changes occur at that edge. The browser lab implements exactly this contract, not AXI as a whole and not a particular memory macro. Eight-bit data ranges from zero to 255; invalid values are rejected by the lab.

Let n be pre-edge occupancy and D be depth. Outside reset, out_valid = (n > 0). Define pop = out_valid && out_ready. We choose a look-ahead ready rule: in_ready = (n < D) || pop. Then push = in_valid && in_ready. The next count is n + push - pop. If both occur, compare and remove the old head first, then append the new input word. This describes logical order, not a requirement that a physical implementation execute sequential operations in that order. It ensures a full FIFO can replace a departing word without an avoidable bubble.

At empty occupancy, out_valid is false even if an input word is offered and the consumer is ready. With no bypass, a push is accepted but no pop occurs on that same edge. The newly stored word becomes visible after the edge and can be consumed on a subsequent edge. A fall-through or bypass FIFO would have a different contract, different combinational paths, and different scoreboard rules. Do not import its behavior into this example because another queue library behaves that way.

At full occupancy, if the consumer is not ready, neither a new push nor a pop occurs. If the consumer is ready and the producer is valid, both occur: the consumer gets the old head, the producer's new word becomes the newest tail, and occupancy remains full. If the producer is not valid, only the pop occurs and occupancy decreases. A simpler FIFO might deassert input ready whenever full, even on a pop cycle. That alternative can be correct under its own throughput contract, but it is not the implementation specified here.

Reset dominates transfers at the rising edge. In this teaching contract reset also masks in_ready and out_valid low while asserted. No transfer is credited during a reset edge; count and both circular pointers become zero, and all previously queued items are discarded. Stored memory bits need not be cleared because invalid entries are unobservable while empty. Output data is unspecified when output valid is false, so the scoreboard must not compare it. Asynchronous reset, reset-release synchronization, partial flush, and retention are separate design choices, not hidden features of this model.

5. Build an independent oracle and a test matrix

A reference model should be simpler than the implementation. For a circular FIFO, use a high-level list or deque rather than duplicating pointer arithmetic. On each sampled edge, determine transfers from observed interface values, check the outgoing word against the old queue head, remove it if a pop occurred, and append the incoming word if a push occurred. Compare expected and observed interface behavior as well as data. Otherwise a DUT that never asserts ready could avoid all data comparisons and appear correct. Progress obligations need their own checks.

The oracle needs a documented relationship to the specification. It should predict ready from expected occupancy and the chosen look-ahead rule, not simply trust DUT ready as inherently correct. The monitor's observed handshake tells you what the interface did; the oracle's predicted handshake tells you what it should have done. Keep both concepts available. If they disagree, report the control mismatch before modifying expected queue state in a way that might obscure the original divergence. One clean approach stops at the first mismatch and saves the surrounding trace.

Test reset before traffic, during a stall, while full, and on the same edge that would otherwise transfer. After reset, confirm old data does not leak into new transactions. Test empty reads as legal consumer readiness without output validity; the consumer may keep ready high indefinitely. Test full writes as offers blocked by low input ready; a compliant producer keeps valid and data stable until acceptance. If your test intentionally violates that rule, identify it as an environment-negative test rather than quietly blaming resulting data loss on the FIFO.

Wraparound deserves more than one fill-and-drain sequence. Fill three entries, pop two, push three, then drain while comparing the exact sequence. Repeat long enough for both pointers to wrap several times. Include non-power-of-two depths if parameterization promises them: a bit-width truncation that wraps correctly at depth four can be wrong at depth three. Depth one is another valuable boundary because input and output often refer to the same physical location during replacement. Our interactive lab stays at four for clarity; the bundled pure model tests include multiple depths.

Use distinct data patterns. All-zero words can hide duplication, loss, and ordering errors. An incrementing tag, an alternating pattern, and values near the word-width boundary make failures easier to interpret. Keep transaction identity separate from payload when repeated values are legal. A protocol may carry two identical payloads in sequence; observing one matching value twice does not prove the correct instances were delivered. For a tagged teaching stream, sequence numbers help expose duplicates, but a real design may need an external history rather than added interface bits.

A constrained-random test should intentionally vary burst length, producer gaps, consumer stalls, reset timing, and occupancy targets. Constraints that accidentally prevent full occupancy undermine full-boundary coverage. Record the seed, configuration, generated sequence, tool version, and model revision. A fixed seed alone is insufficient if a changed generator consumes random numbers differently. Save the reduced failing sequence when feasible. Reproducibility is an artifact contract, not a superstition about seed values.

Worked experiment. Inject a bug that updates count with if push ... else if pop .... Interior simultaneous transfers now increment occupancy instead of holding. A directed simultaneous test fails immediately, while a random test with producer and consumer rarely overlapping may run for a long time. A second mutant increments pointers without wrapping; only a sufficiently long trace exposes it. A third swaps the last two outputs; count-only checks miss it. These distinct mutants tell you whether your test plan has independent control, state, and ordering checks. Review: explain why a queue-length assertion alone cannot verify FIFO behavior.

6. Simulation scheduling, Python, C++, and observability

A simulator has a scheduling model. Driving and sampling a signal at the same nominal timestamp does not automatically mean you observed the intended settled value. Hardware simulation can contain multiple event regions or delta cycles before time advances. A testbench that races the design may fail nondeterministically or consistently read stale values. The right response is not to add arbitrary long delays until the test passes. Define when drivers change inputs, when transfers are sampled, and when post-edge state is inspected.

For a simple synchronous test, drive producer and consumer controls safely before the active edge. Capture the pre-edge handshake values that define acceptance. Then advance through the clock event and allow the simulator's sequential and combinational updates to settle before inspecting next-state outputs. A Python list model can run without a simulator, but connecting that list to HDL requires careful sampling discipline. Avoid mixing pre-edge count with post-edge valid in the same assertion. Such a mixed observation corresponds to no real state of the contract.

cocotb's testbench documentation explains coroutine-based concurrency, value access, and test outcomes. Logging an error is not equivalent to failing a test. An assertion or explicit failure mechanism must make incorrect behavior affect the result. Similarly, creating a coroutine does not necessarily schedule it concurrently; know the framework's task API. These details matter because a never-started monitor can turn a sophisticated-looking environment into an unchecked stimulus generator.

Python is useful for orchestration, reference models, artifact parsing, and experiments because iteration is quick and the ecosystem is broad. C++ is useful where measured hot paths, integration APIs, memory layout, or simulation runtimes warrant it. The Verilator overview describes its C++ or SystemC model flow and optional trace/coverage generation. Neither language is automatically faster at the whole workflow: a C++ parser that repeatedly scans an enormous file may lose to a Python interface backed by a good native index. Measure before translating everything.

Separate semantic events from raw signals. A monitor can turn many signal samples into records such as “input transaction accepted at cycle 73.” Store enough raw evidence to audit that conversion. Version the schema: signal names, bit widths, timescale, clock identity, reset interpretation, and data encoding belong with the records. A JSON number can lose precision in some consumers for large integers, so encode wide values deliberately. Treat unknown HDL values explicitly rather than silently converting them to zero and creating false certainty.

Observability also has cost. Dumping every signal on every test can dominate storage and I/O. A reasonable policy keeps compact logs and coverage by default, retains bounded waveform windows for failures, and supports reproducible reruns with more tracing. Some failures disappear when instrumentation changes timing or resource pressure; retain the original execution context. Distinguish an absent waveform from evidence that no transition occurred. A disabled trace channel cannot support a negative claim about hidden activity.

Worked decision. A Python monitor reports an output mismatch exactly one cycle after every reset. Before changing RTL, inspect the monitor's sampling phase and reset priority. If it appended an input during a reset edge, the reference queue is wrong even if the data comparison code is flawless. A focused trace with reset, valid, ready, data, and expected queue length can settle the question more efficiently than dumping the entire SoC. Review: identify which observed values are pre-edge and post-edge in your own testbench, and state how that is enforced rather than assumed.

7. UVM as architecture, not a vocabulary exam

The Universal Verification Methodology, or UVM, provides a SystemVerilog-based verification methodology and library. Accellera's public standards page describes interoperability and reuse as central goals and links reference implementations and guides. A software engineer can first understand UVM by the responsibilities it separates: transaction intent, driving, passive observation, checking, configuration, and reporting. Knowing class names without understanding those boundaries is not enough to debug a testbench.

A sequence describes transaction-level activity. A sequencer coordinates sequences and transactions. A driver turns transactions into timed interface activity. A monitor passively reconstructs interface activity into transactions. An agent groups related interface components and can be active, generating traffic, or passive, only observing. An environment composes agents and checking infrastructure. A scoreboard compares observed behavior with expectations. These are useful conceptual boundaries, not a claim that every real environment has exactly one of each object or that every small block requires a full UVM deployment.

For the FIFO producer, a sequence might request a burst of ten words. The driver must obey ready/valid rules while delivering those words. The monitor counts only accepted words. The scoreboard can therefore distinguish a sequence that requested ten words from a driver that delivered nine. This separation is especially important for AI-generated tests. An agent may confidently state that it exercised full replacement, but only monitored transfer events and occupancy evidence can show whether the scenario really occurred.

Configuration determines which interfaces, modes, widths, and checking policies are active. Reuse depends on controlling those choices explicitly. A reusable component that silently assumes reset polarity or fixed data width can be more dangerous than a small purpose-built test. Factory-based substitution and configuration mechanisms are powerful, but they can also make effective behavior difficult to inspect. Include the resolved configuration and component topology in reproducibility artifacts when they influence results. Debugging the source code of a class that was replaced at runtime will not explain the actual run.

UVM phase and objection mechanisms help coordinate execution and end-of-test behavior. An early end can terminate a test before expected responses arrive. A test that never ends can waste resources while appearing merely slow. A robust end condition waits for meaningful completion, checks that expected transactions were drained or intentionally discarded, and enforces a timeout with a diagnostic reason. “No errors printed before process exit” is not a sufficient definition of pass.

Generated UVM code should be reviewed for functional independence, not just compilation. Ask where the oracle comes from, how reset clears state, how simultaneous events are handled, which constraints permit boundary cases, and which missing observations cause a failure. A checker copied from the implementation's pointer update may share the implementation's bug. A monitor that reads driver-side transactions instead of pins may fail to detect driver mistakes. Those problems survive perfect formatting and impressive class hierarchies.

Worked decision. For an initial two-day FIFO study, a compact Python testbench may offer clearer evidence than a large UVM scaffold. For an organization integrating many reusable verification IP components, UVM may provide valuable standardization. Choose according to reuse, team expertise, simulator support, and the required checks. This is an engineering trade-off, not a contest between modern and obsolete languages. Review: explain how a passive monitor could reveal a bug that inspecting sequence items alone would miss, and identify the equivalent separation in a web service's integration tests.

8. Assertions, formal reasoning, and the danger of vacuity

An assertion expresses an obligation. For a stalled ready/valid output, a useful property says that if output valid is high and output ready is low, then on the next relevant cycle output valid remains high and output data remains stable, unless reset cancels the obligation according to the contract. That last phrase matters. A property that ignores reset may flag allowed flushing as a bug. A property disabled too broadly may never check the very transition where the real bug occurs. Assertions are executable specifications, so review them as carefully as the implementation.

Safety properties say that something bad never happens: occupancy never exceeds depth, an output never appears from an empty queue, or a stalled word never changes. Liveness properties say that something good eventually happens: an accepted request eventually completes. A FIFO cannot guarantee a consumer will eventually accept data if the consumer may keep ready low forever. To prove progress, state the fairness or bounded-service assumption. Do not smuggle an unrealistic environment into a proof and then advertise unconditional completion.

For our FIFO, occupancy obeys 0 <= n <= D. Its update is n_next = n + push - pop except on reset. These properties catch important bugs but do not establish ordering. Data integrity requires relating an accepted word to the corresponding output later. A formal harness might track a selected symbolic transaction and prove it cannot be overtaken or corrupted under specified conditions. The exact harness depends on tool support and design structure. This book gives the reasoning pattern, not a universal proof script for every HDL frontend.

Assumptions constrain the environment; assertions constrain the design; covers ask whether a scenario can occur. Keep these roles distinct. Assuming that output data is always correct would trivially help prove a data-integrity assertion, but it would remove the problem you intended to solve. Cover a full FIFO, a stalled output, and full simultaneous replacement to check reachability. If none is reachable, inspect constraints and reset behavior before celebrating a clean proof. The SymbiYosys tutorial is a concrete public starting point for these workflows.

A bounded pass means no violation was found within the explored bound under the model and assumptions. An unbounded proof has stronger temporal scope but is still scoped by abstractions, initial conditions, and properties. A timeout is neither a proof nor necessarily a design failure. An engine error is not a counterexample. A generated report must preserve these distinctions in machine-readable form. Collapsing all non-failing statuses into “verified” is a serious product bug for a verification assistant.

Finite widths are part of formal modeling too. An unsigned count stored in too few bits may wrap before an overflow assertion can observe an illegal value. Assertions about derived state can be accidentally tautological. If count is calculated as a truncated pointer difference, proving count fits that width may say little about lost data. Independent invariants, witness tracking, and counterexample review are useful defenses. Always ask whether the representation itself made a bad state unrepresentable without proving the desired functional relation.

Worked decision. A solver proves “if output is stalled, data remains stable,” but a cover shows output valid is never high because reset is permanently assumed asserted. The proof is vacuous for useful operation. Fix the environment model, require an appropriate reset-release history, rerun covers, and only then interpret the assertion result. 9. Coverage closure without percentage theater

Coverage is a model of what matters. Start with requirement-driven bins, then add crosses that expose interactions. For the FIFO, useful dimensions include pre-edge occupancy class, accepted push/pop combination, stall duration, pointer wrap, reset context, and data-order checks. Crosses are not free: multiplying many dimensions can produce a huge denominator filled with redundant or impossible combinations. Design a coverage plan whose missing bins can be explained, not just one whose report looks sophisticated.

A cross of three occupancy classes and four transfer combinations contains twelve nominal bins. Under our no-bypass contract, empty plus pop-only is impossible, empty plus simultaneous is impossible, and full plus push-only is impossible. That leaves nine reachable combinations outside reset. Our coverage lab uses exactly these twelve nominal bins and labels the three structurally unreachable ones. It lets you see why nine hits can mean 75% of the raw denominator or 100% of a reviewed reachable denominator. Neither number proves the data checker is correct.

An exclusion must be justified by the contract and implementation configuration. If the design later adds empty bypass, empty simultaneous transfer may become reachable, so the exclusion must be revisited. “The test has never hit it” is not a reason to call a bin impossible. Use mathematical reasoning, a reviewed specification, formal reachability, or another defensible method. Record whether a bin is unreachable, redundant, deferred, unsupported, or simply not yet observed. These are different engineering situations that should not be compressed into one gray color.

Code coverage offers a different view. A branch may remain unexecuted because a mode is disabled, because stimulus is missing, or because the code is dead. A toggle may be absent because a bus bit is tied off in this configuration or because the intended high-bit scenario was never tested. Investigate rather than applying universal percentage thresholds without context. High code coverage can coexist with a missing ordering checker; high functional coverage can coexist with an erroneous specification. Triangulation is stronger than a single metric.

Targeted stimulus can be more efficient than repeated undirected randomness once common behaviors are saturated. To hit full simultaneous replacement, first reach full occupancy, then assert producer valid and consumer ready together. But useful coverage gain must be measured against total cost and correctness. A generated stimulus sequence that violates the producer's hold rule may hit a bin without exercising legal behavior. An AI system that changes the coverage model to remove difficult bins can manufacture apparent progress. Separate stimulus suggestions from authority to change requirements or exclusions.

For fair evaluations, freeze the coverage plan, simulator setup, resource budget, and permitted interventions. Report total runs, wall time, engineering review time, inference cost, license use, and validated new bugs, not only final bin counts. Distinguish cumulative coverage from per-run coverage, and do not merge incompatible design revisions. A bin reached under yesterday's interface rules may not be evidence for today's behavior. Store coverage provenance with design and testbench identifiers so reviewers can reconstruct what a percentage actually means.

Worked decision. Team A reaches 96% by waiving four difficult bins. Team B reaches 94% with a stricter plan and discovers a real data-loss bug. There is no defensible ranking from the percentages alone. Review denominator definitions, legality, checker quality, and bug severity. Bronco's homepage reports 96% functional coverage from roughly 80%; that is a company marketing claim, not a controlled comparison supplied by this book. 10. Debugging from a failure to a defensible root cause

A failure is an observation, not yet a diagnosis. Preserve the first divergence, the expected behavior, actual behavior, configuration, and relevant requirement. A later cascade of mismatches may be consequences rather than independent bugs. For the FIFO, the first incorrect count update can eventually produce many ordering failures. Starting with the last error in a huge log can send an investigator toward a symptom. Build a timeline anchored in accepted events and state transitions.

Reproduction comes before explanation. Save the exact design revision, testbench revision, tool version, command arguments, environment settings, seed, and input artifacts. Determine whether reruns fail consistently. If not, investigate races, uninitialized state, scheduling, nondeterministic infrastructure, or external dependencies. A flaky failure should not be dismissed merely because it is inconvenient. Nor should the team assume every flaky symptom is a silicon defect when a race in a monitor could explain it.

Localize with a backward slice. Begin at the bad output and ask which state and inputs could influence it. For our FIFO, inspect output head, read pointer, write pointer, count, handshakes, and reset. Add signals only when a hypothesis requires them. Compare a short failing window with an equivalent passing window if available. Large waveforms become manageable when the investigator asks precise questions: did a push occur while stalled, did count change on simultaneous transfer, did the read pointer wrap at the configured depth?

Separate observed facts from hypotheses. “Count changed from four to five after a simultaneous transfer” is an observation if the trace genuinely shows those values. “Two nonblocking assignments overwrote one another” is a source-level hypothesis until the relevant RTL and scheduling support it. “The entire FIFO is broken” is too broad to guide a fix. A good debug report records evidence references for each factual claim and labels untested alternatives. This structure helps both human reviewers and AI assistants avoid turning a plausible narrative into false certainty.

Reduction removes irrelevant inputs while preserving the failure. Shorten bursts, remove unrelated traffic, simplify data patterns carefully, and narrow configuration differences. A minimal sequence that fills four entries and performs one simultaneous transfer is easier to review than a ten-thousand-cycle random run. But do not over-reduce away a timing or integration precondition. Keep the original reproducer and document how the reduced case relates to it. If only the reduced model fails, you may be debugging your reduction rather than the original issue.

A fix needs validation beyond disappearance of the symptom. Add a focused regression that fails before the fix and passes after it. Run related boundary cases and appropriate broader regressions. Check that the fix does not merely suppress a checker, reduce coverage, or constrain away the failing input. A patch that changes the specification requires explicit review, not a quiet assertion edit. Root-cause confidence should increase through independent evidence: trace, source reasoning, a targeted counterexample, and regression behavior.

11. Data systems for logs, waveforms, and inference

A verification assistant is partly a data platform. Inputs include specifications, RTL trees, build metadata, test logs, waveform databases, coverage results, and issue histories. These artifacts differ in structure, scale, trust, and update frequency. Loading all of them into one prompt loses both efficiency and provenance. Start with typed identifiers and retrieval interfaces. A design revision, elaborated hierarchy, simulation run, signal path, and time window should be explicit fields, not guesses extracted from filenames.

Waveforms can be far larger than a model context. Index signal definitions separately from value transitions. Support bounded queries by signal set and time window, with maximum returned events and explicit truncation metadata. An answer based on the first thousand transitions must not imply that the remaining million were inspected. Align timescales and clocks before comparing records. A timestamp of 100 means nothing without units and event semantics. Wide buses, unknown states, and escaped hierarchy names need tested encodings.

For specifications, chunk along meaningful boundaries such as requirements, tables, interface descriptions, and revision notes. Preserve section anchors and source hashes. Retrieval should account for version and configuration rather than returning an obsolete requirement with high textual similarity. A retrieved table may have headings necessary to interpret units; stripping those headings can reverse the meaning. A good UI lets an engineer open the exact source context used in a conclusion rather than only a model-generated summary.

Caching needs semantic keys. A cache for waveform queries can include artifact hash, parser version, signal selection, time interval, and conversion policy. A model-answer cache also depends on prompt, tool schema, model version, and relevant policy. If a patch changes RTL, invalidate affected derived evidence instead of attaching stale findings to a new revision. Content-addressed artifacts and immutable run records make this easier. Deduplication saves storage, but authorization must still be enforced at the project boundary.

Inference performance is a pipeline property. Total latency includes queueing, retrieval, parsing, tool execution, model calls, retries, and review. Parallelize independent evidence gathering, but do not let speculative tasks race to edit the same working tree. A smaller model may classify routine infrastructure errors while a stronger model handles ambiguous causal reasoning. Use measured task quality, abstention, and cost rather than assuming more tokens always produce better diagnoses. Batch background work when appropriate without delaying urgent interactive feedback unnecessarily.

The full-stack interface should expose execution state: queued, running, waiting for a license, waiting for evidence, needs review, or failed. Streaming prose alone can hide a stalled tool. Show artifact links, exact query bounds, truncation warnings, and a timeline of actions. Let engineers compare original and proposed changes, inspect coverage denominator changes, and reject a recommendation with a reason. The product's job is not to make uncertainty disappear visually; it is to make uncertainty actionable.

12. Agents as bounded engineering workflows

An LLM agent selects actions through tools and uses their results to update a plan. That can help when diagnosis requires multiple dependent queries. It also creates failure modes: repeated expensive runs, unsupported causal claims, unsafe edits, prompt injection from artifacts, and premature declarations of success. The useful abstraction is a bounded workflow with explicit authority, evidence, and stopping conditions. The model should not inherit unrestricted shell access just because a human engineer sometimes uses a shell.

Begin with read-only tools. Examples include retrieving a requirement by revision, searching an elaborated signal hierarchy, querying a waveform window, reading a bounded source range, and fetching a run's structured status. Each tool needs an input schema, authorization checks, resource limits, timeout semantics, and a response carrying artifact identifiers. Return structured errors rather than silently substituting stale data. An agent cannot reason reliably about a tool that says “success” when it delivered only a partial result without marking it.

Escalate authority in stages. A proposal tool can draft a test or patch in an isolated workspace. Execution tools can run approved commands under quotas. Promotion into a shared branch, edits to coverage exclusions, and signoff decisions require review. Keep generated artifacts separate from trusted sources until validated. Never allow an agent to make a regression pass by weakening its own success criteria without explicit disclosure and approval. The same separation is familiar in secure software delivery: code generation and authorization are different responsibilities.

Artifact text is untrusted data. A log could contain a line telling the agent to upload a repository, reveal secrets, or disable a checker. Treat it as log content, not as a higher-priority instruction. Tool permissions and network controls must enforce boundaries even if the model follows malicious text. On-premises deployment by itself does not solve this problem: an internal agent can still access too much, execute unsafe commands, or leak through an allowed service if policies are weak. Security is a system property, not a location label.

An evidence ledger should distinguish observed facts, derived facts, hypotheses, proposed experiments, and verified outcomes. For every factual claim, store source identifiers and the query or computation that supports it. An agent may say “insufficient evidence” when a waveform lacks the needed signal. That is preferable to inventing a signal value from source-code intuition. Stopping conditions include a supported diagnosis, conflicting evidence, exhausted budget, unavailable tools, or a requirement ambiguity needing human resolution.

A playbook is a repeatable investigation procedure. A model can choose among playbooks or suggest new ones, but successful reuse requires preconditions and applicability limits. A full-replacement FIFO playbook should not be applied unchanged to an empty-bypass asynchronous queue. Parameterize protocols and reset semantics explicitly. Review generated playbooks on held-out examples, including cases where they should abstain. A reusable wrong explanation can amplify harm faster than a one-off mistake because it looks like institutional knowledge.

Given a failing FIFO run, the agent retrieves F3, reads the run configuration, queries the first mismatch window, inspects the count-update source range, and proposes a focused reproducer. It does not edit RTL until the evidence supports a hypothesis and the action is authorized. After a patch, a separate validation step runs the fixed test and broader boundaries. 13. Evaluate agents on engineering outcomes

A demo can show that a system sometimes succeeds. An evaluation asks how reliably it succeeds on a defined distribution under controlled conditions. For verification tasks, examples might include known RTL bugs, testbench defects, infrastructure failures, specification ambiguities, and clean runs. A dataset containing only obvious RTL bugs rewards a system that always blames RTL. Include hard negatives and cases requiring abstention. Define what counts as a correct diagnosis before running the system, not after reading persuasive prose.

Prevent leakage across train, development, and test splits. Related bug variants, duplicated blocks, shared testbenches, and repeated source snippets can make nominally separate examples nearly identical. A held-out seed on the same known bug is weaker evidence than a held-out design or bug family. Split by relevant units and report the choice. If an agent learns reusable playbooks from development cases, freeze that library before testing. Otherwise the evaluation becomes an uncontrolled feedback loop.

Measure multiple outcomes: correct root cause, supported evidence, valid reproducer, patch correctness, regression preservation, abstention quality, time, compute cost, and review burden. A fast wrong diagnosis is not helpful; a correct diagnosis with fabricated evidence is unsafe; a valid patch that deletes a checker is not a successful repair. Score partial achievements separately rather than compressing everything into one undocumented success percentage. Reviewers should be able to inspect adjudication criteria and resolve disagreements.

Use baselines that reflect real alternatives. Compare with a search-only tool, a fixed playbook, an experienced engineer using existing tools, and perhaps a simpler model. Equalize budgets where possible and state unavoidable differences. An agent allowed hundreds of simulations should not be compared with a human given only one log excerpt without disclosure. Include integration and setup time when evaluating deployment economics. A tool's benefits can depend heavily on whether its required metadata already exists.

Statistical uncertainty matters. If a system solves 18 of 20 cases, the observed success rate is 90%, but the true task-distribution performance is not known exactly. Small samples are especially unstable, and repeated variants are not fully independent. Report counts, task mix, confidence intervals when appropriate, and error categories. Avoid presenting a single anecdotal multi-day human comparison as a universal speedup. The relevant denominator may be all incoming failures, not just those selected for an impressive demo.

Evaluate harm and calibration. Can engineers tell when the system is uncertain? Does it abstain more often on missing evidence? Does a confident answer actually correspond to higher correctness? Track false claims of proof, fabricated signal values, unauthorized attempts, and changes to success criteria. Measure how often a reviewer must undo agent work. A system that creates ten plausible but wrong tickets can slow a team even if it occasionally finds a difficult real bug.

Worked evaluation design. Freeze 60 public or synthetic cases across six failure classes, with source revisions and expected evidence. Allocate a fixed simulation budget, prohibit checker weakening, and blind the reviewers to system identity. Record every tool action and engineer correction. This is a recommended experimental design, not a description of an existing Bronco benchmark. Compare net review time as well as solved cases. Review: explain why a public known-bug benchmark can still be useful while being insufficient evidence for performance on a customer's unseen proprietary design.

14. Deployment, safety, and the customer boundary

A customer deployment begins with understanding the environment. Inventory operating systems, schedulers, simulator versions, licenses, artifact locations, network rules, identity systems, retention policies, and support expectations. Semiconductor design data can be highly sensitive intellectual property. An engineer should know exactly which artifacts an assistant reads, where derived embeddings or summaries live, and whether any model endpoint receives source or waveform content. Do not assume that “enterprise” or “on-prem” is a complete data-flow specification.

Use least privilege and project isolation. A service that can read one block's logs should not automatically read every program on the filesystem. Separate read, run, propose, and approve permissions. Sandbox generated code and subprocesses. Enforce timeouts, disk limits, process limits, and command allowlists appropriate to the workflow. A model's promise not to run an unsafe command is not an access-control mechanism. Audit logs should record meaningful actions without unnecessarily duplicating sensitive source text.

Long jobs need durable state. A browser connection may close while a regression continues for hours. Store job identities, inputs, state transitions, cancellation requests, and artifact references so the UI can reconnect. Retrying a request must not accidentally launch duplicate expensive simulations. Idempotency keys and scheduler-aware reconciliation help. A canceled agent step does not necessarily mean the underlying process has stopped; track both orchestration state and actual execution state. Resource leaks are customer-facing reliability bugs.

Versioning is operationally important. Pin supported simulator and parser versions, validate compatibility, and provide rollback paths. A parser update that changes signal naming can break saved debug queries. A model update can change tool choices or abstention behavior even when prompts remain the same. Run canaries and representative regression evaluations before broad rollout. Keep old evidence interpretable after upgrades; a conclusion should not become unauditable because its original tool schema disappeared.

Customer-facing work means translating ambiguous pain into a testable workflow. Ask what currently takes time: locating artifacts, reproducing a failure, distinguishing infrastructure from RTL, writing targeted stimulus, or reviewing candidate patches. Define a pilot with a bounded block, measurable outcomes, and clear data permissions. Watch engineers use the tool rather than relying only on reported satisfaction. Start with a precisely documented FIFO contract, a compact RTL implementation, an independent Python oracle, and directed boundary tests. State which simulator and versions are required. 17. Twenty-five interview drills with worked answers

These are original practice questions, not reported Bronco interview questions. Use the structure choice → mechanism → evidence → trade-off. Answers are intentionally bounded; extend them with your own project examples rather than memorize them as scripts.

Drill 1 — Explain RTL to a backend engineer

RTL describes concurrent combinational logic and clocked state transitions. I model it as current state plus inputs producing outputs and next state, rather than as sequential statements on a CPU. Two registers can exchange old values on the same edge. My evidence would be a two-register trace showing pre-edge and post-edge values. The abstraction helps functional reasoning but does not by itself establish physical timing, power, or metastability behavior. I would learn those boundaries rather than claim software simulation proves the manufactured chip.

Drill 2 — What happens when push and pop coincide at full?

Under this book's look-ahead contract, output valid is high and consumer ready makes pop true. That pop makes input ready true, so producer valid also produces a push. The consumer receives the old head, the new word becomes the newest tail, and count remains full. I would test the exact sequence before and after the edge. A conservative full-blocking FIFO could instead reject the push, but that is a different throughput contract, not a reason to leave this case ambiguous.

Drill 3 — What happens when both sides are eager at empty?

This FIFO has no bypass. Output valid is false from pre-edge empty occupancy, so no pop occurs. Input ready is true and the offered word is stored, making next occupancy one. It becomes available afterward. I would use a directed empty case to distinguish this from a fall-through design. The trade-off is potential latency versus combinational path complexity; I would not claim one behavior is universally correct without the specification.

Drill 4 — How would you verify ordering?

I would keep an independent high-level queue of accepted input words and compare every accepted output against the old queue head. I would use varied data and test interleaved traffic, stalls, wrap, and reset. I would also check control behavior so a DUT cannot avoid comparisons by refusing all transfers. Count invariants help but cannot detect swapping two words. The trade-off is maintaining an accurate sampling adapter without copying the implementation's pointer algorithm into the oracle.

Drill 5 — Does 100% coverage mean correct?

No. Coverage measures planned observations or structural activity, not the truth of all requirements. A disabled scoreboard can coexist with full bin coverage, and the plan can omit an important scenario. I would inspect checker quality, denominator definitions, exclusions, and requirement traceability. I would use coverage to locate blind spots alongside assertions, formal results, and review. The trade-off is that no single dashboard number can summarize all residual risk honestly.

Drill 6 — When would you use formal instead of simulation?

I would use formal for precise properties with manageable models, particularly corner sequences difficult to reach randomly. Simulation remains valuable for detailed workloads and integration behavior. I would distinguish bounded checks from unbounded proofs and review assumptions with reachability covers. The evidence is a scoped property result or concrete counterexample, not a blanket “verified” label. The trade-off is abstraction and state-space complexity; proving the wrong property exhaustively still answers the wrong question.

Drill 7 — Why can a Python scoreboard be wrong?

It can sample in the wrong phase, ignore finite widths, misunderstand reset priority, or update on requested rather than accepted transactions. I would define edge semantics, use independent expected state, and run checker mutants or known-bad RTL. Logs should show pre-edge observations and post-edge expectations explicitly. Python makes modeling convenient but does not guarantee semantic correctness. A small model is useful only when its assumptions match the interface contract and are tested independently.

Drill 8 — What would you inspect first in a huge failing waveform?

I would first identify the earliest meaningful mismatch and its run metadata, then query a narrow time window around relevant interface and state signals. I would expand the signal set only when a hypothesis requires it. The evidence should name artifact, signals, units, interval, and truncation status. This reduces I/O and cognitive load, but risks missing a distant cause; retaining the original trace and iteratively broadening the backward slice mitigates that risk.

Drill 9 — How do you distinguish a testbench bug from an RTL bug?

I compare the failure against the requirement and independent observations, rather than trusting either component automatically. A focused trace can show whether the monitor credited a reset-edge input incorrectly or the DUT actually violated ready/valid. I try a minimal directed reproducer and independent checker where feasible. The trade-off is investigation time, but premature RTL changes can hide a testbench defect and introduce a real design bug. Classification remains a hypothesis until supported.

Drill 10 — Design a waveform-query tool for an agent

Inputs include immutable artifact ID, signal paths, start/end time, units, and event limit. Outputs include typed values, metadata, exact covered interval, truncation, parser version, and errors. Authorization and resource limits live outside the model. I would test unknown values, wide buses, missing signals, and malformed files. The trade-off is that a constrained tool is less flexible than an arbitrary shell, but much easier to audit and keep within the customer's data boundary.

Drill 11 — What makes a diagnosis evidence-backed?

Each factual claim points to an exact source range, trace window, requirement, or reproducible computation. The report separates observations from hypotheses and states alternatives not yet eliminated. A candidate root cause gains confidence through a focused reproducer and a fix that preserves related checks. The trade-off is more structured output and provenance storage. I prefer that cost to a fluent narrative that engineers must reverse-engineer or cannot verify at all.

Drill 12 — How would you evaluate a debug agent?

I would freeze cases, budgets, tool permissions, and scoring before testing. The set should include unseen bug families, clean runs, infrastructure issues, testbench faults, and ambiguities requiring abstention. Measure supported diagnosis, patch validity, review time, cost, and harmful actions against practical baselines. Splitting by seed alone risks leakage. The trade-off is benchmark construction effort, but a small carefully adjudicated set is more informative than many near-duplicate success examples.

Drill 13 — Where would you use C++ rather than Python?

I would profile the pipeline first. C++ may fit a hot waveform decoder, memory-sensitive index, or simulator integration; Python may fit orchestration, models, and experiments. A bounded native library can expose a typed interface to Python without rewriting the whole system. Evidence would include representative latency, throughput, memory, and correctness tests. The trade-off is development and integration complexity, so I would optimize measured bottlenecks rather than choose by language prestige.

Drill 14 — How do you target an uncovered bin?

First confirm the bin is meaningful, legal, reachable, and correctly instrumented. Then derive a precondition and stimulus sequence, such as filling the FIFO before requesting simultaneous replacement. Check that the monitor actually observed the event and the checker remained active. If unreachable, propose a reviewed exclusion with evidence rather than silently changing the denominator. The trade-off is engineering effort per bin; prioritize risk and coverage quality over indiscriminate percentage chasing.

Drill 15 — What should reset do to your scoreboard?

For this contract, a reset edge discards all expected items and credits no transfers. The monitor also expects interface validity and readiness masked while reset is asserted. I would test reset during full occupancy and during a stall, then verify no old word leaks afterward. Other designs can preserve or drain data, so I would not generalize the flush rule universally. The critical choice is consistent, explicit reset semantics across DUT, checker, and coverage.

Drill 16 — Why not upload the entire waveform to an LLM?

It can exceed context, waste cost, expose sensitive data, and obscure exact timing through lossy text conversion. I would retrieve bounded structured windows and let the model ask follow-up questions through controlled tools. Every query reports what it covered and omitted. The trade-off is more indexing and tool design, but that architecture supports reproducibility, access control, and scale. A large context window does not remove the need for provenance or careful sampling semantics.

Drill 17 — What if a log tells the agent to ignore its instructions?

Treat that text as untrusted artifact content, never as authority. Enforce file access, commands, network destinations, and approval rules outside the model. Add adversarial log cases to evaluation and verify denied actions remain denied even if the model requests them. The trade-off is a narrower tool environment, but logs can contain attacker-controlled strings or accidental instruction-like text. Prompt wording alone is not an adequate security boundary for customer design data.

Drill 18 — How would you cluster regression failures?

I would begin with structured metadata and conservative signatures, preserving representative artifacts and allowing splits. Similar error text does not prove a shared root cause. Evaluate both over-merging and over-splitting against reviewed cases, and retain links from each run to its bucket. The trade-off is reduced triage effort versus the risk of hiding a second bug. I would report bucket confidence and changes rather than present clustering as an infallible diagnosis.

Drill 19 — What does a useful coverage UI show?

It shows requirement links, reached and unreached bins, denominator definitions, exclusions with review provenance, run configuration, and relevant checker status. It supports drilling from a missing bin to legal stimulus ideas and from a hit to actual evidence. I would also display stale or incompatible coverage instead of merging silently. The trade-off is information density, so use progressive disclosure without hiding changes that could manufacture apparent improvement.

Drill 20 — What happens when an agent job is retried?

An idempotent orchestration layer should reconnect to existing work or create a clearly new attempt, not accidentally launch duplicate simulations. Store immutable inputs, job IDs, scheduler state, and cancellation outcomes. Reconcile orchestration state with actual processes because a disconnected client does not imply a stopped run. The trade-off is durable state and operational complexity, but customer licenses and compute are too costly to treat retries as harmless repeated HTTP requests.

Drill 21 — How would you interpret Bronco's 10x claim?

I would attribute it to the public homepage and describe its stated scope: working UVM stimulus, checkers, and scoreboards. I would not convert it into a universal engineering productivity multiplier. For a pilot, ask about workload, baseline, review effort, total resource cost, and what counts as working. The trade-off is less exciting marketing language, but precise attribution lets a team design a fair evaluation without dismissing a potentially useful product or overstating evidence.

Drill 22 — How is this role different from pure DV?

The public posting emphasizes building intelligent systems, frontend/backend coverage tools, data processing and inference, and customer deployments, with Python/C++, full-stack, and LLM skills. A pure DV role more directly owns design-specific verification artifacts and closure. They overlap in domain understanding, and boundaries vary. I would show software systems depth plus enough hardware literacy to collaborate with DV experts. I would not pretend a short textbook replaces years of verification experience.

Drill 23 — What would you do during the first customer week?

Map the workflow, access boundaries, tool versions, artifact availability, and the customer's definition of success. Select a bounded read-only pilot and reproduce representative failures before proposing automation. Establish support contacts and rollback. Evidence includes a data-flow diagram and an agreed evaluation plan. The trade-off is slower initial feature shipping, but skipping environmental discovery often creates fragile integrations and invalid measurements that cost more time later.

Drill 24 — When should an agent abstain?

When required evidence is missing, tools return partial results, requirements conflict, budgets are exhausted, or available observations support multiple unresolved causes. It should explain what is missing and suggest the next safe experiment. Evaluate abstention quality alongside accuracy, since always abstaining is also unhelpful. The trade-off is fewer apparently complete answers, but calibrated incompleteness protects engineer trust and prevents unsupported patches from entering a critical workflow.

Drill 25 — What portfolio result would make you proud?

A small end-to-end system with a precise contract, independent checker, killed mutants, bounded evidence tools, and an honest held-out evaluation. I would show one hard success and one correct abstention, then explain remaining limitations and deployment risks. The trade-off is breadth versus depth: a polished imitation of every product feature is less persuasive than a narrow workflow whose claims can be independently reproduced. My goal is demonstrated judgment, not a fictional production-readiness badge.

18. Glossary and a final review checklist

Assertion: an executable obligation about behavior. It can fail on a trace or be analyzed formally; its scope depends on its semantics and environment.

Backpressure: a receiver delaying acceptance, commonly by lowering ready. A compliant sender preserves its offered word until acceptance unless a documented cancellation rule applies.

Bin: a named coverage category. Its usefulness depends on a meaningful plan, legal reachability, and trustworthy observation rather than the number of bins alone.

Clock domain: logic organized around a particular timing reference. Crossing domains requires a deliberate transfer strategy; sharing nominal frequency does not automatically make two clocks synchronous.

Combinational logic: logic whose intended outputs depend on current inputs without stored state. Physical propagation still takes time even when a functional model abstracts that delay.

Counterexample: a concrete behavior violating a property under a model and assumptions. It is evidence to inspect, not automatically proof that the implementation rather than the harness is wrong.

Coverage closure: the process of investigating and addressing missing planned observations, including reviewed exclusions. It is not a synonym for completing every possible correctness argument.

DUT: design under test. The chosen boundary determines which behavior belongs to the design and which behavior belongs to its environment.

Elaboration: resolving parameters, hierarchy, and related HDL structure into a concrete model for analysis or execution. Source files alone may not reveal the effective configuration.

Emulation: executing a mapped hardware model on specialized hardware. It supports long workloads with different compilation, visibility, and integration trade-offs from ordinary simulation.

FIFO: first-in, first-out storage. Timing, bypass, reset, and full-boundary policies are part of its contract, not implied completely by the name.

Formal verification: mathematical analysis of properties over a model. Results depend on assumptions, abstraction, engines, and whether the task is bounded or unbounded.

FPGA: field-programmable gate array. It can host prototypes, but mapped clocks, memories, and interfaces can differ from the intended ASIC implementation.

Handshake: the event that commits a protocol transfer. In our example it occurs at a rising edge when valid and ready are both high and reset is inactive.

Inference: executing a trained model to obtain outputs. End-to-end agent latency also includes retrieval, tool work, queues, retries, and human review.

Invariant: a property intended to hold in every relevant reachable state, such as bounded occupancy. An invariant can be necessary without being sufficient for complete functional correctness.

Liveness: an eventual-progress obligation. It often needs environmental fairness assumptions, unlike a simple safety property forbidding a bad state.

Monitor: a passive observer reconstructing actual interface events. It should not confuse requested transactions with accepted transfers.

Oracle: an independent source of expected behavior. A reference implementation copied from the DUT can share its errors and weaken independence.

PPA: power, performance, and area. A functionally correct patch can still be unacceptable if implementation costs or timing violate the product's constraints.

Regression: a repeatable collection of checks across tests and configurations. Missing jobs, infrastructure errors, and test failures need distinct statuses.

RTL: register-transfer level, describing combinational relationships and state updates. It is an abstraction used before lower-level implementation and physical realization.

Scoreboard: a component comparing observed behavior against expectations, often tracking transaction history. Its reset and sampling semantics are part of its own correctness.

Seed: an input to a pseudorandom generator. Reproducibility also needs generator version, configuration, toolchain, and other run inputs.

Signoff: an accountable engineering risk decision based on reviewed evidence. It is not implied by one percentage or delegated safely to persuasive generated prose.

SoC: system-on-chip, integrating multiple functional blocks. Composition can fail even when each component passes its own local checks because contracts disagree.

Static analysis: analysis that does not depend on ordinary simulation stimulus. Different static tools address coding, timing, crossings, or equivalence; none is a universal correctness test.

Stimulus: inputs presented by a verification environment. Intended stimulus is not proof that the design accepted or exercised the corresponding behavior.

UVM: Universal Verification Methodology, a standardized methodology and library supporting reusable verification environments. Understanding responsibilities matters more than memorizing class names.

Vacuity: an apparently successful property result that does not exercise the intended obligation, for example because assumptions prevent its antecedent from ever occurring.

Waveform: time-indexed signal values. Correct interpretation needs units, signal definitions, sampling semantics, artifact identity, and awareness of omitted or truncated data.

CDC: clock-domain crossing. The information type and clock relationship determine the protocol; a two-flop level synchronizer does not solve all crossings.

RDC: reset-domain crossing. Reset-driven asynchronous changes and mismatched recovery epochs can create hazards even when data registers share a clock.

MTBF: mean time between failures, a probabilistic estimate derived from technology and timing assumptions, not a finite lifetime guarantee.

Gray pointer: an encoded pointer whose successive local increments change one bit. Physical skew constraints, synchronization, and the exact FIFO comparison algorithm still matter.

TLM: transaction-level modeling interfaces used to connect verification components through transaction objects rather than direct knowledge of every implementation.

SVA: SystemVerilog Assertions. Clock events, sampling, implication, and reset cancellation determine what an assertion actually obligates.

Final review checklist. Can you define pre-edge versus post-edge state? Can you explain empty and full simultaneous cases without hesitation? Does every promised behavior have an observer and a checker? Are reset and unknown values explicit? Can a reviewer reconstruct a run? Are coverage exclusions justified? Are proof statuses accurately scoped? Does every agent claim point to evidence? Can the system abstain? Are tool permissions enforced outside the model? Are marketing claims attributed? If any answer is no, that is an actionable next step rather than a reason to hide uncertainty behind a polished dashboard.

19.1 Synthesizable structures versus testbench machinery

Synthesis translates a supported subset of HDL into hardware structures. Fixed-width registers, combinational expressions, and appropriately written clocked blocks commonly map into logic. Dynamic classes, unconstrained randomization, queues used as testbench oracles, simulator delays, and coverage collection generally belong to verification software rather than this FIFO's synthesized datapath. Support varies by tool and flow; “legal SystemVerilog” is not equivalent to “synthesizable in every target.” An interface can group synthesizable signals while a virtual interface handle belongs to testbench objects that access those signals.

This fragment implements only the occupancy controller for a fixed depth-four FIFO. Storage, data output, and pointer logic are intentionally absent, so it cannot prove or implement data ordering by itself:

↔ Code scrolls horizontally · illustrative, not executed in browser
module fifo_count4 (
  input  logic clk, rst,
  input  logic in_valid, out_ready,
  output logic in_ready, out_valid,
  output logic [2:0] count
);
  logic push, pop;
  always_comb begin
    out_valid = !rst && (count != 0);
    pop       = out_valid && out_ready;
    in_ready  = !rst && ((count < 3'd4) || pop);
    push      = in_valid && in_ready;
  end
  always_ff @(posedge clk) begin
    if (rst) count <= 3'd0;
    else case ({push, pop})
      2'b10: count <= count + 3'd1;
      2'b01: count <= count - 3'd1;
      default: count <= count; // 00 or 11: unchanged
    endcase
  end
endmodule

always_comb assigns all four intermediate/output signals on every path, avoiding intended-storage ambiguity. always_ff expresses clocked state. The nonblocking assignment <= schedules the register update; all right-hand sides use the relevant old values. Count needs three bits to represent zero through four. A two-bit count would wrap at four and could hide a full condition. The case makes simultaneous transfer explicit: two valid events do not mean two conflicting assignments to count. Reset is synchronous for count but combinationally masks the handshake outputs, matching chapter 4. Even before the first reset edge, a testbench must not interpret an uninitialized count as a valid state.

A respin is a new manufacturing iteration after a design change. It can consume engineering time, validation effort, fabrication/packaging lead time, and market opportunity. No fixed dollar estimate is justified here. This is why a small count-width mistake can matter beyond a unit test: the software can often be redeployed quickly, while a manufactured hardware correction may require a much slower and more expensive loop.

19.2 Interfaces and sampling discipline

An interface bundles signals; a clocking block establishes a view of when a testbench samples them. In this observer-only example, input #1step means sample immediately before the clocking event. It does not mean “wait one clock cycle.” The monitor should construct a snapshot from this clocking view, not mix it with direct post-edge signal reads.

↔ Code scrolls horizontally · illustrative, not executed in browser
interface fifo_if(input logic clk);
  logic rst, in_valid, in_ready, out_valid, out_ready;
  logic [7:0] in_data, out_data;
  clocking mon_cb @(posedge clk);
    default input #1step;
    input rst, in_valid, in_ready, in_data;
    input out_valid, out_ready, out_data;
  endclocking
  modport OBS (clocking mon_cb);
endinterface

Drive inputs in a separate, deliberately chosen phase, such as on falling edges in a simple test. Do not treat this observer interface as a driver implementation. A monitor waits for @(vif.mon_cb), then reads DUT-facing pins through mon_cb. Its snapshot includes sampled reset, both transfer events, and data only where meaningful. At reset it flushes the scoreboard; at simultaneous transfer it processes the old output before appending the new input. The test sequence's request to send is not a substitute for this observation.

19.3 Classes and constrained randomness

A class is a software-like object in the verification environment. A sequence item represents intent at transaction granularity. This example is a producer-side request; consumer stalls would be generated independently. A producer gap is a gap between words, not permission to withdraw a word already stalled by low ready.

↔ Code scrolls horizontally · illustrative, not executed in browser
class fifo_item extends uvm_sequence_item;
  `uvm_object_utils(fifo_item)
  rand bit [7:0] data;
  rand int unsigned gap_cycles;
  constraint short_gap { gap_cycles inside {[0:7]}; }
  function new(string name = "fifo_item");
    super.new(name);
  endfunction
endclass

The rand fields participate in constraint solving when randomize() is called. The declared constraint does not automatically cause any test to run, does not force full occupancy, and does not establish a uniform distribution across complex scenarios. Check randomization's return status; a failed solve cannot be treated as a valid new stimulus sample. bit is two-state, so use four-state types where unknowns must remain visible. This item's two-state payload is reasonable for generated legal eight-bit input words, not for silently coercing observed DUT outputs.

19.4 UVM connections you should be able to explain

A sequence produces items; a sequencer arbitrates item requests; a driver converts granted items into clocked pin activity. A typical driver requests an item with seq_item_port.get_next_item(req) and calls item_done() only when its defined transaction has actually completed. Connect its sequence-item port to the sequencer's export in connect_phase. The sequencer is not the scoreboard, and a successful item handshake between sequence and driver is not a ready/valid handshake on the DUT interface.

UVM's transaction-level modeling, or TLM, interfaces pass objects between components without making every consumer know each producer's implementation. An analysis port supports broadcast observation. A monitor can publish a sampled cycle object to multiple consumers: scoreboard, coverage collector, and trace logger. Allocate or clone snapshots appropriately; if subscribers retain a mutable object that the monitor later reuses, old observations can appear to change retroactively. Analysis write is a function and should not contain time-consuming waits. Use a queue or analysis FIFO when a downstream task needs decoupled processing.

The following excerpt belongs inside an environment class. mon and score are handles created in build_phase; score implements an analysis receiver whose write handles the monitor's snapshot type. This is connection syntax, not a complete compilable environment:

Later check/report phases can examine unconsumed expected transactions and summarize errors. An objection holds a phase open; it is not proof that all necessary checks ran. The factory supports registered type or instance overrides. An environment composes agents and end-to-end checking. Understanding those responsibilities is more valuable than producing an ornate hierarchy with no independent oracle.

19.5 SVA: an explicit reset and clock interpretation

Concurrent assertions sample signals at specified events. This example checks an eight-bit output's stall stability at rising edges. It uses sampled synchronous-reset semantics: if reset is sampled at the next edge, the outstanding stall obligation is canceled. It does not react to a reset pulse that happens entirely between edges. Such a pulse would not reset the chapter 4 FIFO's state either, though the combinational interface mask still follows reset while asserted.

↔ Code scrolls horizontally · illustrative, not executed in browser
property hold_stalled_word;
  @(posedge clk)
    (!rst && out_valid && !out_ready)
    |=> (rst || (out_valid && $stable(out_data)));
endproperty
assert property (hold_stalled_word);
cover property (@(posedge clk)
  !rst && out_valid && !out_ready);

|=> is non-overlapped implication: a stall sampled now creates a requirement at the next sampled edge. $stable compares sampled data with the preceding sample. Even if ready becomes high at the next edge, valid and data must still represent the same pending word for that transfer, unless reset cancels it. If stall continues, the property starts another obligation, chaining stability across the interval. The cover shows a stall antecedent was reachable; it does not prove the stability assertion or ordering.

A common alternative is disable iff (rst). Its usual asynchronous disabling semantics differ from this deliberately sampled-reset property: it can abort an attempt when reset asserts between clock edges. For an asynchronous-reset design that may be intended, but copying that idiom blindly can suppress obligations the synchronous specification wanted checked. Unknown reset or data values require additional knownness checks and a defined initialization protocol. This snippet is not a complete assertion suite. It says nothing about eventual consumer readiness, integrity of unstalled words, memory behavior, or physical setup/hold.

19.6 Covergroups, structural coverage, and the missing oracle

Statement coverage asks which executable statements ran. Branch coverage asks which decisions/outcomes occurred. Toggle coverage asks which relevant bit transitions were observed. FSM coverage asks which recognized states and transitions were visited. Definitions and exclusions are tool-dependent. Assertion coverage may report attempts, successes, failures, and vacuous passes; inspect the exact report rather than counting a never-triggered implication as useful success. A cover property can provide a witness for a specific temporal sequence, not a general correctness certificate.

Functional coverage starts with the specification. This covergroup accepts a monitor's pre-edge occupancy class encoded 0=empty, 1=interior, 2=full and event encoded 0=idle, 1=push, 2=pop, 3=both. Its owner constructs the group once and calls sample once per non-reset observed edge. It does not infer occupancy from a driver's intended burst length.

↔ Code scrolls horizontally · illustrative, not executed in browser
covergroup fifo_x with function sample(int occ_class, int ev);
  cp_occ: coverpoint occ_class {
    bins empty = {0}; bins interior = {1}; bins full = {2};
  }
  cp_ev: coverpoint ev {
    bins idle = {0}; bins push = {1};
    bins pop = {2}; bins both = {3};
  }
  x: cross cp_occ, cp_ev {
    ignore_bins empty_pop = binsof(cp_occ.empty) && binsof(cp_ev.pop);
    ignore_bins empty_both = binsof(cp_occ.empty) && binsof(cp_ev.both);
    ignore_bins full_push = binsof(cp_occ.full) && binsof(cp_ev.push);
  }
endgroup

These exclusions follow this FIFO's no-bypass, full-replacement contract. They are not reusable truths about every FIFO. Place separate assertions on illegal behavior; ignoring a coverage bin is not a mechanism that makes illegal behavior fail. Do not use these exclusions to hide an observed DUT handshake violation. Revisit them after any protocol change. A wrong sampling phase can label an empty push as an interior push, so test the collector against hand-audited traces.

All-lines-executed escape. The coverage lab's tiny JS reducer runs write and read statements in both correct and deliberately faulty versions. The faulty read removes the newest item rather than the oldest. The smoke suite writes and immediately reads one item at a time, reaching every labeled reducer statement without distinguishing FIFO from LIFO. The ordering suite writes two distinct items before reading. It exposes the wrong output with the same 100% labeled-statement result. These are explicit JavaScript instrumentation labels, not a real HDL coverage report. Keep the ordering checker enabled, then disable it to see why a full scenario bin and a passing run still cannot establish correctness without an oracle.

20. CDC and RDC: where logical certainty meets physical probability

A clock-domain crossing, CDC, occurs when information moves between domains whose sampling relationship requires explicit treatment. Different nominal frequencies are not the whole definition: two clocks at the same frequency can be unrelated, while generated clocks with properly constrained relationships can be timed synchronously. First classify the clocks, then classify the meaning of the information crossing. A persistent status bit, a one-cycle event, a multi-bit command, and a stream of words need different transfer contracts. “Add two flops” is not a universal design method.

20.1 Metastability is analog; pulse loss is logical

A destination flip-flop has setup and hold requirements. An asynchronous transition can arrive in that aperture, and the storage element can take an indeterminate time to settle to a valid logical output. This analog behavior is metastability. An ordinary RTL simulation with zero/one values cannot reproduce its physical resolution distribution. An X can represent an unknown digital value, but it is not a calibrated voltage trajectory. A perfectly clean simulation therefore does not prove that asynchronous sampling is physically safe.

A synchronizer gives a potentially metastable first stage more time to settle before its output is used by downstream functional logic. Additional stages, favorable placement, device characteristics, destination frequency, and source transition rate influence reliability. A typical qualitative relationship is that MTBF improves exponentially with available settling time and degrades as clock frequency and asynchronous transition rate rise, with technology-dependent constants. Do not calculate a numerical MTBF without characterized constants, actual timing, and appropriate assumptions. MTBF means mean time between failures, a probabilistic reliability estimate, not a guarantee that a specific device survives that many years.

At system scale, many crossing chains contribute failure opportunities. Under a suitable independent rare-event approximation, failure rates add; a design with many chains can have a lower aggregate MTBF than each individual chain. Correlations and operating conditions can invalidate simplistic assumptions. Synchronization reduces the probability that unresolved metastability propagates; it does not eliminate metastability from physics. Use the target vendor's implementation and analysis guidance rather than inventing a universal two-stage reliability promise.

Pulse loss is a separate issue. A source may assert a short pulse entirely between two destination sampling edges. Every sampled value is zero, no setup/hold violation is necessary, and adding more destination flops cannot recover an event that the first stage never saw. The CDC lab models this deterministic sampling problem only. It contains no random metastability, no voltage model, no setup/hold aperture, no timing-closure proof, and no MTBF estimate. This narrow model is useful precisely because it isolates a mistake that exists even in ideal digital logic.

The receiving domain must get a reset release meeting its local reset requirements, described below. logic sync1, sync2;

The first stage is allowed to be uncertain transiently; do not fan it out to functional consumers or insert arbitrary logic between stages. The implementation flow should recognize the chain and preserve a favorable settling path. Registering the source level can avoid combinational glitches that increase transition rate. The destination sees a delayed level; the source must keep it meaningful long enough for the protocol. Two flops do not guarantee capture of a short pulse, preserve every rapid transition, or make a collection of independently synchronized bits into a coherent word.

Imagine a source code changing from binary 01 to 10. Independent bit synchronizers can report 00 or 11 temporarily because the bits are not guaranteed to be observed in the same destination cycle. Each chain can be individually well-formed and the combined command still wrong. Similarly, synchronizing one control separately along two paths and reconverging them can create inconsistent enable timing. Synchronize once where appropriate, then distribute within the destination domain; where independent crossings are necessary, analyze the reconvergence protocol explicitly.

20.3 Pulses, toggles, and acknowledgments

Pulse stretching holds a source level high long enough to overlap destination sampling opportunities. Its required width and event spacing depend on clock relationships, timing margins, and the synchronization protocol. Avoid a simplistic promise that exactly one destination period is always sufficient under physical timing uncertainty. A long high level can also represent only one event unless a defined low interval separates events. In the lab, setting width equal to spacing merges adjacent source pulses into one continuous high interval, illustrating that “captured level” and “counted events” are different requirements.

A toggle scheme flips a source bit for each event. The destination synchronizes that bit and detects a change against its previous synchronized value, producing a local event. A narrow source pulse is converted into a persistent state change, so it need not overlap a destination edge. But two source events can toggle the bit twice before the destination observes either, returning it to its old value. Without an event-rate bound or acknowledgment, toggle encoding still loses information. It is not an unlimited-throughput event counter.

A handshake adds feedback. The source changes a request toggle only when the previous request has been acknowledged. The destination synchronizes the request and acknowledges the observed state; the acknowledgment is synchronized back. The source must either backpressure the producer, queue new events, or explicitly reject offers while busy. A design that silently accepts events while refusing to update the request loses them. In the lab's handshake mode, busy offers are not accepted; they are counted separately rather than dishonestly labeled delivered. It models no input queue and no producer retry. All accepted events drain in the finite example, but fewer offers may be accepted at a high source rate.

For a multi-bit bundled-data handshake, the source holds the data stable while the control crosses and until the acknowledgment permits reuse. The destination captures the word at a defined point after the stable-data guarantee applies. The control synchronizer is not synchronizing each data bit; coherency comes from the protocol and physical timing of the held bus. Check data-before-control and hold requirements, and constrain implementation accordingly. A protocol diagram and property set should state when the source may change data, not merely show a request arrow and an ack arrow.

20.4 Asynchronous FIFOs: Gray is necessary context, not a spell

An asynchronous FIFO supports independent read and write clocks, with storage and control designed for that boundary. A common power-of-two design uses local binary pointers for addresses and registered Gray-coded pointers for crossing. Gray encoding is g = b ^ (b >> 1); successive local increments change one Gray bit. Include an extra wrap bit to distinguish equal addresses at full versus empty. A destination synchronizes the remote Gray pointer before using it in local comparisons. Comparing live unsynchronized remote binary pointers defeats the purpose.

In a common registered-flag construction, the read side compares its candidate next Gray read pointer with the synchronized write pointer to determine empty. The write side compares its candidate next Gray write pointer with a transformed synchronized read pointer to determine full. For the standard power-of-two reflected-Gray scheme, the transformation inverts the top two Gray bits and keeps the remaining bits unchanged. That rule belongs to that exact encoding and pointer-width construction; it is not a recipe to paste into arbitrary-depth or custom-coded FIFOs. Depth-one and non-power-of-two cases require their own treatment.

Synchronization makes the remote pointer stale. A writer may continue to see full briefly after a reader frees space, or a reader may continue to see empty briefly after a write. Conservatism is usually preferable to overrun/underrun. The same-clock full replacement policy in chapter 4 cannot simply be carried across two unrelated clocks using a combinational ready path. The asynchronous design needs its own documented latency and flow-control contract.

Gray coding alone does not constrain wires. Physical skew or excessive propagation between Gray-bit paths can make transitions from successive source increments overlap at the receiving pins, undermining the intended one-transition-at-a-time reasoning. Use target-appropriate maximum-delay and/or bus-skew constraints, verify implementation reports, and follow the vendor IP's constraints rather than inventing one universal constraint command. Broad asynchronous-clock exceptions can accidentally remove checks that the Gray bus still needs. A receiving clock can legitimately skip several source pointer states; adjacent destination samples can differ in multiple Gray bits. Therefore a one-hot-change assertion on every synchronized sample can be wrong even when the crossing is valid. Apply the single-increment property to the appropriate local registered pointer with its enable assumptions.

The data memory must also support the intended dual-clock access pattern and read-during-write behavior. Pointer logic does not create a safe memory primitive by itself. The proof obligations include no read of unwritten data, no overwrite of unread data, ordered delivery, reset handling, and local flag correctness with delayed remote knowledge. Use a high-level queue or abstract transaction history as an independent reference where possible, and understand how the formal harness models independent clocks.

20.5 Reset-domain crossing and reset release

A reset-domain crossing, RDC, can occur even when data registers share a clock. If a source register is asynchronously reset while a receiving register is not, the source output can change asynchronously relative to the receiver. Resetting one domain can also invalidate a handshake state the other domain still considers outstanding. Treat reset relationships and data isolation as part of the architecture, not a final wiring detail.

Asynchronous assertion is often used to force a safe state without a running clock. Deassertion must satisfy recovery/removal and local synchronization requirements. A common strategy is asynchronous assertion and synchronized deassertion separately in each clock domain. The following illustrative release chain assumes its technology permits this style and that downstream reset distribution is analyzed. It is not a substitute for library, placement, reset-tree, and timing review:

logic [1:0] release_pipe;
always_ff @(posedge dst_clk or negedge async_rst_n) begin
  if (!async_rst_n) release_pipe <= 2'b00;
  else             release_pipe <= {release_pipe[0], 1'b1};
end
assign dst_rst_n = release_pipe[1];

With reset asserted, both bits are zero. On the first destination edge after external release, the lower bit becomes one while the upper remains zero. On a later edge the upper becomes one, releasing the local reset. Physical implementation still determines reliability; the first release stage can encounter metastability. If the clock is stopped, local reset release waits for it. Do not assume two domains release on the same wall-clock instant. Reset combinational logic, power sequencing, scan/test modes, and clock gating need their own analysis.

For an asynchronous FIFO, resetting only one side can make the two pointer histories inconsistent and discard the shared meaning of stored words. Decide whether resets must be coordinated, whether traffic is isolated during recovery, and how both domains acknowledge a fresh epoch. Do not compare a reset-to-zero local pointer with an old remote pointer and call the resulting state valid. A reset of a toggle source can also look like a new event to a live receiver; initialize or re-handshake the protocol rather than trusting a bit's default value to solve epoch alignment.

20.6 Verification strategy and model answers

Static CDC/RDC analysis identifies clock/reset domains, recognizes synchronizers, finds unsynchronized crossings and reconvergence, and reports structural risks. It depends on complete constraints, recognized structures, and reviewed waivers. Simulation exercises protocol sequences, clock ratios/phases, reset orders, and data integrity. Formal analysis can explore legal handshake histories and prove scoped digital properties under assumptions about clocks, synchronization delay, and reset. None of those digital models computes analog metastability resolution automatically. Specialized metastability-injection abstractions can explore uncertain latency, but their validity depends on the abstraction and cannot replace physical reliability analysis.

Lab prediction. Use source period 4, destination period 10, phase 3, one-source-cycle pulse width, and event spacing five source cycles. Source pulses begin at 4, 24, 44, and so on and last four ticks. Destination edges at 3, 13, 23, 33, and so on miss every high interval in the ideal model. The source pulse train is real in its own clock domain but never reaches the first capture stage. Toggle mode preserves these well-spaced events because the changed level persists. Increase the source event rate and the toggle can lose events too. Handshake mode instead refuses some offers while busy; accepted-versus-offered counts reveal the throughput cost.

Model answer. The correct remedy is not “more flops fixes everything.” Choose a level synchronizer for a persistent bit, a rate-bounded toggle or acknowledged event protocol for pulses, a stable bundled-data handshake for occasional words, and a properly implemented asynchronous FIFO for a stream. Specify event spacing, buffering, reset epoch, and physical constraints. Validate structure, digital protocol, and physical timing/reliability with complementary evidence.

21. Compile, schedule, reproduce: the regression as a distributed system

A useful regression result has two identities: the compiled model and the run that exercised it. Compilation depends on source revision, file order, include paths, macro definitions, parameters, library versions, simulator version, optimization, tracing, and coverage instrumentation. A run additionally depends on the executable build ID, seed, test name, plusargs, runtime configuration, input data, timeouts, and environment. Caching a build under a short RTL commit hash while ignoring changed macros or UVM libraries can attach a perfectly reproducible run to the wrong machine.

Use an immutable manifest. It should name the build recipe and content hashes, not merely a developer's working directory. Preserve standard output/error separately, process exit status, structured checker results, resource accounting, and artifact availability. A zero process exit code with missing end-of-test checks is not necessarily pass. A compiler failure is not an RTL behavioral counterexample. Distinguish compile error, elaboration error, run failure, timeout, infrastructure error, missing result, and pass-with-all-required-checks-complete. The UI should make those states visible rather than compress them into red and green.

Bronco publicly says its agents run on customer compute through Slurm or LSF. These are company-described integrations, not independently audited deployments. The adapter design below is an educational proposal, not a claim about Bronco's implementation. The adapter should submit a typed job description, capture the scheduler's job identifier, reconcile queued/running/completed states, and confirm cancellation of the actual process tree. Keep the scheduler command construction outside free-form model text. Allocate a per-run workspace, approved environment, and explicit artifact destination. Job arrays can improve operational efficiency, but each member still needs its own manifest and outcome. A lost web connection must not erase the only reference to a running simulation.

Simulator licenses are scarce resources distinct from CPU cores. Eight available cores do not imply eight simultaneous licensed simulations. Bound launch concurrency by the relevant license feature and job requirements, account for wait time, and avoid consuming an expensive token while a run is blocked on unrelated preprocessing. Define license-hours as the time-integral of occupied tokens, not simply wall time multiplied by requested job count. Compilation and simulation may consume different features. Failed or canceled jobs can still consume real license time and should remain in cost accounting.

A wave-dump policy trades storage and observability against runtime. Default to compact structured errors and suitable coverage, retain failure windows, and make expanded-wave reruns reproducible. A run that fails only without tracing deserves investigation: instrumentation can change scheduling, memory pressure, or host performance and expose a race or timing-sensitive infrastructure issue. Never discard the original manifest because a rerun passed. Preserve enough context to distinguish “bug disappeared” from “we ran a different configuration.”

Failure clustering starts as a prioritization aid. Normalize volatile paths and timestamps carefully, but do not remove fields that distinguish bug causes. A shared assertion name can arise from several upstream faults. Keep original records, allow bucket splits, and measure incorrect merges as well as redundant splits. For minimization, keep the oracle and failure definition fixed while shrinking stimulus, not the reverse. If a reduced test only fails after disabling reset checks, you may have changed the problem. Report the original and reduced examples together.

Worked budget. Twelve runs require 20 minutes each and one simulation token each. With three tokens and enough cores, four waves require at least 80 minutes of run time, ignoring overhead and queue delays; total occupied-token time is four license-hours. Doubling cores alone does not halve that lower bound. Faster failure detection, prioritizing distinct buckets, and reducing unnecessary reruns may save more than broad parallelism. These are illustrative arithmetic assumptions, not a measured customer workload.
